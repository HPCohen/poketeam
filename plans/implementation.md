# Implementation record

The approved plan is preserved in [approved-plan.md](approved-plan.md). Its consequential decisions were approved before implementation: Rust/Axum with SQLx and PostgreSQL, a separate worker in the same image, anonymous cookie ownership, transactional sprite storage, deterministic type-based counter heuristics, and current-team seven-day notifications. These avoid additional services and keep publication atomic. Accounts, frontend work, production provisioning, battle simulation, and globally optimal search remain outside this delivery.

Implementation uses explicit SQL and one crate with modules for configuration, catalog models, HTTP/identity/teams, counter scoring, and synchronization. Small related operations share modules rather than adding service/repository layers. This organization is reversible. Upstream URLs use an explicit host allowlist; HTTP is opt-in for the local fixture server. OpenAPI is generated from the same schemas and handlers as the server.

Validation and any implementation limitations are recorded below as work completes.

## Delivered components

- `backend/`: Rust crate, locked dependencies, embedded initial migration, commands `serve`, `worker`, `sync`, `migrate`, and database-independent `openapi` export. Modules separate catalog, identity, teams, counter scoring, notifications, synchronization, configuration, and HTTP policy/errors.
- Migration: owner token hashes, content-addressed sprite assets, retained Pokémon, complete type chart, teams and constrained ordered members, run outcomes, structured changes, and catalog publication state. Run sequence numbers make restart/status ordering deterministic even when injected clock timestamps coincide. Species IDs are deliberately not globally unique across retained Pokémon: changing a species’ default variety must preserve the former variety for existing teams. Each incoming active snapshot still requires unique species IDs.
- Catalog: active-only pagination/search/type filters; retained detail records; local immutable sprite URLs; revision/content ETags; readiness and refresh status. Readers that combine multiple queries use repeatable-read snapshots so a publication cannot mix revisions in one response.
- Identity/teams: 256-bit random HttpOnly cookies, SHA-256 token hashes, rolling expiry, exact mutation Origin validation, bounded JSON requests, owner-scoped SQL, transactional ordering changes, and row-locked optimistic revisions. Authenticated responses are not cached. Selection validation holds a shared catalog-state lock so availability cannot change during a write.
- Counters: deterministic power and rival scoring/search, exact integer ±5% validation, reserved active source members during unavailable replacement, single replacements capped at ten passes, opponent explanations and shared weaknesses. Blocking searches hold one of two bounded CPU permits even if their HTTP caller disconnects.
- Synchronization: explicit host/redirect allowlist, four shared request permits, download bounds/timeouts, three transient attempts with jitter and Retry-After, complete default-variety discovery, normalized field comparisons, per-scan sprite downloads, atomic publication, initial-import silence, relevant relationship events, 30-day history pruning, dedicated advisory-lock connection, persistent scheduling, crash recovery, and cancellation rollback.
- Notifications: inclusive preceding-seven-day/current-team query, event-level deduplication, affected team IDs, structured differences, descriptions, pagination, and injected clock.
- `Dockerfile`, `compose.yaml`, `.env.example`: one non-root image for API/worker/migrations, PostgreSQL health dependency and persistent volume. An optional `RUST_IMAGE` build argument supports mirrors of the same pinned toolchain image; the default remains the official Rust image. Database migration remains an explicit deployment command.
- `.github/workflows/backend.yml`: pinned Rust version, formatting, warning-free Clippy, unit/integration tests with PostgreSQL, OpenAPI drift check, container build; no live PokéAPI in CI.
- `README.md`, `docs/api.md`, `docs/operations.md`, and `scripts/`: one-page design/quick start, React/TypeScript contract, configuration and health/scheduling, backup/restore, generated API checks, and reproducible fixture demonstration.

All of these choices implement the approved architecture. No additional irreversible architectural decision was needed. The default-form preservation, clock-tie ordering, cache behavior, and bounded counter execution are implementation details that protect the approved guarantees.

## Verification results

- `cargo check --locked`, `cargo fmt --check`, and `cargo clippy --all-targets --locked -- -D warnings` pass.
- Full `cargo test --locked`: **19 passing tests**, including nine pure counter tests and ten isolated PostgreSQL/local HTTP fixture integration scenarios. Integration scenarios cover the complete REST contract, current-team alerts, exact expiry, sprite byte replacement at stable upstream URLs, all consumed differences, chart-only relevance, unavailable/default-form preservation, transactional rollback, bounded retries/download size, pagination, persisted restart scheduling, owner expiry, simultaneous revision updates, overlapping scans, cancellation lock release, and process-level execution of every command with graceful SIGTERM shutdown and restart scheduling.
- OpenAPI export contains 10 unique paths and 13 operations, with all 63 local schema references resolving. The checked-in document matches runtime generation; DELETE’s required JSON body is included.
- The reproducible demo passes; actual captured output is in `docs/demo.md`. Baseline has zero alerts; changing one selected Pokémon’s HP and sprite produces one deduplicated alert across two teams; repeating the scan adds zero events; seven days plus one second expires the alert. Both immutable image URLs remain readable and serve different bytes.
- Test networking and Docker require sandbox escalation on this machine. The initial sandbox-only integration attempt was denied local sockets; rerunning with approved local network access passed. No live PokéAPI calls were used.

No unresolved product or architecture questions arose during implementation. Frontend implementation and production hosting remain the separately approved follow-up scope. Production origin/credentials/backup destinations should be configured at deployment time using `docs/operations.md`.

## Container verification limitation

Docker Compose configuration and the multi-stage Dockerfile are present, and PostgreSQL 17 ran successfully for all integration tests. The local application-image build could not finish its 252.76 MB Rust base-layer download at the available transfer rate. The original Docker Hub attempt and an identical-digest Google public-mirror attempt were stopped after confirming the same severe slowdown. **Application container build/runtime verification remains pending**, and no image-build success is claimed. The CI workflow runs the complete container build. Native executable tests independently verified migration, API process health/session startup, worker initial import, restart scheduling, one-shot synchronization, OpenAPI export, and graceful SIGTERM shutdown. The development PostgreSQL Compose service remains running; successful isolated SQLx test databases are cleaned up by SQLx.
